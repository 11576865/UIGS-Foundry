- Search for exact combined `FFmpeg.wasm excludes attachment output AVStreams + reattach original Blob.slice master` did not reveal another registered Candidate; do not promote merely because one CI environment passed.

## Observed problem
- Before this design, WORKERFS already allowed >1GB real PCM media-packet MKV mux in 0.1027, while **128MiB original attachments pass / 256MiB originals fail** when ffmpeg.wasm directly maps original attachment AVStreams. Controlled five-case [#39610097982](https://github.com/11576865/MKV-Fast-Muxer/actions/runs/39610097982): with total 256MiB original attachments, 2×128, 4×64, and 8×32MiB all OOM during formal output; 128MiB 2×64 and 4×32 passed. This links failure more strongly with total original FileData payload allocation, not raw object count alone. Does not establish a universal 256MiB ceiling.
- Merely using `WORKERFS` for source input cannot prevent the FFmpeg output muxer from buffering/copying original attachments while constructing the Matroska header.

## Bounded two-lane candidate
1. Bind the **same actual immutable source browser File** and reject source graph shapes outside the verified class **before** loading/running FFmpeg.wasm: one complete `Attachments` master, finite exact Segment, no unsupported Segment CRC, no original `Tags` or `Chapters` (especially UID-targeted relationships), no arbitrary unknown layout grant.
2. Mount source read-only with already-delivered `WORKERFS` / exact File reference. Execute real Chromium FFmpeg.wasm with explicit `-map 0:v:0 -map 0:a:0 -map 1:s:0 -c copy -c:s srt` and **never** map original attachment streams into the output. FFmpeg.wasm owns the A/V+new-subtitle packet streams only. It returns a bounded, small no-attachments MKV Blob; failure is terminal, never silently fall back to full input MEMFS.
3. The independent browser `Blob.slice` path references the original Matroska `Attachments` master bytes without reading large FileData as a single JS array; reindexes appended master with the output's fixed-width Segment VINT, the first valid CRC-protected `SeekHead`, an adjacent `Void` slot sized to keep offsets invariant, and recomputed `SeekHead` CRC32 using the existing `src/ebml-crc32-bounded.js`. If the reserved index layout cannot fit, reject; do not silently relocate Cluster/Cues or claim graph preservation.
4. Deliver a new Blob via browser download, **not** mutate original. Independently inspect final MKV's video/audio/new subtitle, exact attachment inventory, `mkvextract` every original attachment + full SHA-256, untouched source SHA, and byte-level SHA-256 of **every ordered original/output encoded audio and video packet**. No success state if any native audit fails.

## Remaining safety/performance gates before any bounded product promotion
- Formal source and remux metadata parity or explicit no-edit impossibility for `Tags`, `Chapters`, `TagAttachmentUID`, `ChapterUID`, attachments with per-master/nested CRC, atypical `SeekHead`/nonterminal `Attachments`, `Cues`, unknown-size/fragmented Segment and multiple original master ordering. Source-attached FileUID/name/mimetype uniqueness and graph targeting require independent verification; don't assume binary bytes imply complete document semantics.
- Failed, interrupted, changed-source or canceled operations must not leave stale writer authority or a green downloadable artifact. Validate source File object identity and execution-bound revision, including batch/project recovery.
- Real desktop/tablet memory envelope (including browser output data copies), 512MiB/≥1GB original attachments with realistic long media, output persistent-save reliability, and diverse browser engines.
- Explicit authorized limited route and human-readable scoped capability disclosure; never automatically default a general MKV to this research writer. No Canonical update until repeated independent source and real-device evidence supports it.

## 2026-10-23 production audit precondition: bounded large original FileData (PR #188)

Product [PR #188](https://github.com/11576865/MKV-Fast-Muxer/pull/188) targets a separate precondition of this existing S12 Candidate rather than promoting the research-only large-attachment writer. Previously the production `auditPreservedOriginalAttachmentData` compared source/output attachments via whole-`arrayBuffer` WebCrypto SHA-256 with a **32 MiB per-FileData and 64 MiB aggregate budget**; verified S12 research commonly uses individual 64 MiB original attachments, so the existing product result stayed `unavailable` even if bytes were correctly retained.

Proposed change (current exact head `02c03ff17a6300af9e07cf96c80750fa50f39ece`, based on main `2b33a0d0bda4533d8e2d2d064fec963d652906f3`):
- Preserve the original SHA-256 method for bounded small objects. Add an explicit 1 MiB-per-side-chunk, **full-range byte equality** fallback for larger FileData, with a **128 MiB per-attachment / 1 GiB total compared bytes** budget. It does not hash each chunk and pretend it is a whole-file SHA-256.
- Evidence v2 distinguishes `proofMethod=exact-byte-compare, sha256=null, comparedBytes=byteLength` from per-attachment v1 SHA. The finished-output attachment observation projection accepts either only under strict evidence- and count-aware checks; lack of SHA is never reported as a SHA match.
- Test real finite EBML Blob fixtures with 64 MiB original FileData and last-byte corruption; retain explicit unavailable-on-budget refusal. Do not loosen the existing experimental attachment-only writer's 16 MiB per-File ceiling or any current output/UID/Tag authorization.
- Product `main.js` selects this opt-in bounded output audit when a genuine finished MKV already exists. It does **not** authorize S12's temporary Void media-view/Blob reattachment path, or claim media packets, TagTargets, UID graph, FFmpeg source decoder memory, physical tablet memory or durable save.

**Observed testing at intake:** initial head `5eadb81c565da94e56dd298161b2c463d40444aa` failed a legacy source-pattern test and a 64 MiB fixture that incorrectly used a 16 MiB-limited experimental writer. Corrected head `02c03ff17a6300af9e07cf96c80750fa50f39ece` instead constructs a finite Matroska EBML Blob purely for reader audit; exact-head Node unit + Pages/build passed, real S10/Chromium and S12 workflows still running when recorded. **Pending complete CI / not merged / Candidate only**; successful Node cases are not native large-output production acceptance. ## 2026-10-23 S12 cancellation authority must survive a long FileData audit

The S12 bounded FileData bytewise verifier proposed in product [PR #188](https://github.com/11576865/MKV-Fast-Muxer/pull/188) can now scan up to 1 GiB in 1 MiB chunks. The pre-existing UI cancel button terminates ffmpeg.wasm, but has no direct effect on an already-running `Blob.slice().arrayBuffer()` loop. Without separate cancellation checks, an abort could allow the expensive FileData loop to finish and the existing warning-tolerant completion path to publish an output after user cancellation.

Product exact head `2a5e3a7b5dbe07981da2b148a29523719d0161a7` adds explicit `shouldCancel` checks before/after each chunk and around SHA/audit result issuance. The read-only audit returns `unavailable` with zero verified rows upon interruption; the actual product executor additionally throws after checking `cancelRequested || (independent && batchCancelRequested)` to prevent a cancelled artifact from following the normal downloadable warning path. Node tests cover a mid-chunk interruption, initially cancelled task and the binding of the final publication guard. This is **code submitted / exact-head CI pending** (new branch head supersedes prior E2E green). It is a task-control safety property, not media preservation, device-memory or writer proof; no Canonical change.
