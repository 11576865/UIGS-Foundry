# Case: Softmux tablet AI concept images confused functional coverage with visible UI

Date: 2026-10-15
Status: **Case / explicit user rejection of image-based proposals; source-grounded corrected two-screen concepts produced, not user-accepted**
Project: `11576865/MKV-Fast-Muxer`
Evidence class: Direct user feedback + design-document comparison; not runtime browser/UI or implementation acceptance.

## Observed failure
- A request for tablet concept images with **all theoretical functional entry points**, including nonimplemented capabilities, first yielded 9 separate dense wireframes with a text feature inventory per region. A corresponding Figma file was created with nine frame layouts; structural editability checks could not establish usable UI.
- Follow-up raster concepts converted each technical chapter into an always-visible, instructional card/dashboard. They over-emphasized A/B/C/D as separate destinations, included duplicate global nav, and represented execution/audit as independent static feature showcase screens.
- User rejected these results: “自己看看你设计的是UI吗？？？？？＊能不能好好看材料”.
- A subsequent collage continued to show a 3×3 grid of nine pseudo-screens; this was also visibly inconsistent with the promised corrected two-workspace approach and should not be considered accepted UI.
- This is a design-generative failure, not proof of a defect in actual production code.

## Ground-truth design evidence
- `软封工程_未来规划总决议_2026-10-12` D-03: subtitle delivery, composition, validation, and inspection are **orthogonal capabilities**, not four separate states/databases/screens.
- D-05: batch is Recipe + Job Matrix + shared item Inspector + independent queue/outcome **in one task context**.
- D-09 and §9: object-centred dense workspace, no lengthy explanatory cards, redundant object cards, giant buttons, or tablet stacking. Tablet is **composed output/object list + selected Inspector**, source as recoverable drawer; output/risk state stable at lower edge.
- `软封_未来规划与UI知识系统_聊天记录溯源审查_2026-10-13` pp.9,11,13: primary composition surface, batch matrix, viewport-specific two-area tablet projection; pp.8,10,12 describe visual failure criteria, stable identity, and queue semantics.

## Recoverable distinction
**Complete route reachability is not equivalent to simultaneous visual exposure.** Enumerate all product capabilities in a coverage ledger, but locate controls by object ownership, selection, task context and contextual disclosure. The primary screen should contain the currently operative data, editable fields, compact row commands and stable output action—not a feature brochure. Unsupported capabilities should remain discoverable in the appropriate object/menu with explicit limits rather than occupy dedicated decorative feature panels.

## Bounded correction in this conversation
Two static 1365×860 landscape tablet mockup images were produced for:
1. output composition + selected subtitle-track Inspector; source access via drawer; stable output bar;
2. recipe-controlled output Job Matrix + selected EP04 Inspector; state/validation and approved-run controls remain attached to the matrix.
These images are **unapproved illustrative concepts**. They do not validate touch flows, focus/undo preservation, functional completeness, visual quality, real implementation, or full old-feature parity.
